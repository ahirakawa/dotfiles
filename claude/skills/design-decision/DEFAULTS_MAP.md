# 対応表：どのOpus既定を、どのルールで打ち消したか（design-decision）

| # | Opusの既定挙動（打ち消す対象） | 打ち消すルール | 観測可能な挙動差 |
|---|---|---|---|
| D1 | **早すぎる収束**。最初に思いついた案をアンカーにし、精緻化を比較と錯覚する | ステップ1: 選択肢2つ以上＋「構造的に異なる案」1つ以上＋現状維持の強制掲載 | 素のOpusも複数案は挙げるが、最初の案の兄弟案に偏りがちで対比を経ず精緻化に流れることがある。差は複数案の"有無"ではなく、構造的に異なる案の強制と各案「勝つ条件」対比の明示性 |
| D2 | **strawman比較**。形だけの代替案を並べて「比較した」体裁を作る | ステップ1: 各案に「この案が勝つ条件」1行の強制。書けない案は差し替え | 全選択肢に「勝つ条件:」行が存在する（grep可能）。負け確定の案が消える |
| D3 | **訊きすぎて決めない**。選択肢提示＋「要件次第です」で判断をユーザーに投げ返す | 絶対規則: 固定書式「## 推奨」ブロックで終える。質問は「推奨を反転させ即答可能」に限り最大2問。未知は仮定を置いて条件付き決定 | 不確実な判断でも条件付き一択で締める応答に**一貫**する。素のOpusはコミット／確認待ち／二択残しが実行ごとに割れる（差は一択の有無ではなく一貫性） |
| D4 | **基準への文字通り追従**。評価軸を与えると全軸を均等に埋め、加点集計で結論を出し、支配的な軸の判断が蒸発する | ステップ2: 対比より先に決定軸（最大2つ）を宣言。勝ち数決定の明示的禁止。効かない軸は「差なし」で流す | `決定軸:`行が対比表より前に出現する。全軸均等のマトリクス採点が消える |
| D5 | **確信の水増し**。推測を確定事実の口調で語り、前提の脆さを隠す | ステップ3: 前提への【確認済/仮定】タグの強制 | 素のOpusも推測を推測と断ることはあるが散発的。差は区別の有無ではなく、【確認済/仮定】タグによる構造化と一貫性 |
| D6 | **不確実性による先送り**。未知を見つけると「まず確認しましょう」で判断自体を保留する | ステップ3: 未知に「安く潰す方法＋目安コスト」を併記しつつ、仮定を置いた条件付き決定を強制 | 未知があっても推奨ブロックが出る。「〜を確認してから決めましょう」で終わる応答が消える |
| D7 | **ヘッジ癖**。「どちらも一長一短」「ケースバイケース」で責任の所在を曖昧にする | ステップ4: `案:`は一択（「AまたはB」禁止）＋「最有力の反対理由」の強制 | 推奨が常に単数。却下案のsteelmanが毎回文章として残る |
| D8 | **撤回条件なしの決定**。決めた後の監視条件を残さず、決定が信仰になる | ステップ4: 後戻り条件ちょうど1つ、観測可能な数値・イベント限定。「要件が変わったら」は禁止語 | `後戻り条件:`行が毎回存在し、閾値・イベントが具体的に書かれる |
| D9 | **同意バイアス**。ユーザーの傾きを検出すると評価がその案に寄る | 傾き検出時の追加規則: 評価より先に「その案への最強の反論」を書く。反論なしの同意を禁止 | 反論が評価より**先に・構造化されて**出る。素のOpusも反論はするが同意的な書き出しに埋まり、反論後もコミットしないことがある（差はタイミングと形式） |
| D10 | **指示追従の過剰**。プロセスを全案件に儀式として適用（関数名の相談に対比表） | ステップ0: G1〜G4の素通し・即決条件＋「可逆に見える不可逆」（データモデル・公開IF・保存形式）の警告 | 軽微な判断が`即決:`1行で終わる。skillの「勝ち」は表を書くことではなくゲート行を出すこと |

## 検証メモ

- empirical検証時の判定変数として最も頑健なのは:
  (1) 応答末尾に固定書式「## 推奨」ブロック（`案:`/`最有力の反対理由:`/`後戻り条件:`）が存在するか、
  (2) `決定軸:` 行が対比より前に存在するか、
  (3) 判断依頼に対し質問のみで終わる応答が0件か。
  いずれも文字列マッチで判定でき、主観評価が不要。
- 意図的に入れなかったもの: ADR（Architecture Decision Record）ファイルの自動生成。決定の永続化として一見有効だが、相談の多くは口頭壁打ち相当であり、全件ADR化はD10（儀式化→無効化）を誘発する。永続化が要る決定は「## 推奨」ブロックをそのまま貼れる書式にしてあり、保存の判断はユーザーに残す。
