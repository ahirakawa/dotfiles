# worked examples: 判断依頼 → skill適用時の出力

抽象論ではなく、実際の依頼文と実際の出力の対でこのskillの挙動を定義する。
迷ったらこのファイルの粒度に合わせる。

---

## 例1: 「日次バッチ、ストリーミングにした方がいい？」

### 規律なしの既定挙動（こうなってはいけない）

パターンA（早すぎる収束）: 「ストリーミングにはKafkaとFlinkが…」と
移行手順の精緻化を始める。「すべきか」を訊かれたのに「どうやるか」を
答えており、現状維持という選択肢が最初から消えている。
パターンB（決めない）: バッチとストリーミングの一般的な長所短所を
対称に並べ、「要件次第です。鮮度要件を教えてください」で終わる。
比較したふりの教科書の再生であり、判断が1ミリも前進していない。

### このskill適用時の出力

判断ゲート: フル適用（不可逆寄り: 実行基盤・監視・障害対応の作り直しを伴う）

**選択肢**
- A. 現状維持＋日次バッチの信頼性改善（リトライ・遅延検知の強化）
  — 勝つ条件: 下流の意思決定サイクルが日次より速く動いていない場合
- B. マイクロバッチ化（15分間隔。既存のバッチ資産を流用）
  — 勝つ条件: 「日中に数回更新したい」程度の鮮度要求で、運用人員を増やせない場合
- C. ストリーミング基盤へ移行
  — 勝つ条件: 分単位の鮮度に事業価値が実証されており、常時稼働基盤を運用する体制がある場合

決定軸: 鮮度要求の実在性 ＋ 運用負荷 — 技術的に可能かではなく、
「誰がその鮮度を使うのか」と「誰が夜中に直すのか」がこの判断を分ける。
（コスト・拡張性は3案で差はあるが決定的ではない: 差なし扱い）

**前提と未知**
- 【仮定】下流の利用は日次のレポートと意思決定が中心で、分単位で
  行動が変わる利用者は現時点でいない
- 【確認済】現行バッチの失敗率・遅延は運用記録から把握可能
- 未知: 「リアルタイムが欲しい」という声の具体的な用途
  — 安く潰す方法: 要望元に「更新が15分おきになったら何を変えるか」を
  一問聞く（30分。答えが具体的でなければ鮮度要求は実在しない）

## 推奨
案: A（現状維持＋信頼性改善）。ただし上記ヒアリングを1件だけ実施する
根拠: 決定軸の両方でAが勝つ。鮮度要求の実在が未確認のままCへ進むのは、
使われない鮮度のために常時稼働の運用負荷を買う取引になる。Bへの中間
移行も、要求が実在しないなら負債の分割払いにすぎない
最有力の反対理由: 「要求が顕在化してから移行では遅い。基盤は先行投資
すべき」— 正しい場面もあるが、ストリーミング移行は後からでも段階実行
できる（B経由）ため、先行投資の不可逆性プレミアムが成立しない
後戻り条件: ヒアリングで「15分ごとの更新で具体的な業務行動が変わる」
利用者が2件以上特定されたら、Bを起点に再検討する

## 例2: 「この履歴テーブル、SCD Type 2 とデイリースナップショット、どっちがいい？」

### 規律なしの既定挙動（こうなってはいけない）

SCD2とスナップショットの教科書的比較表（ストレージ、クエリ複雑度、
実装難度…）を全軸律儀に埋め、勝ち数っぽい雰囲気で「一般的にはSCD2が
推奨されます」と答える。この判断を実際に分けるのは「訂正・遅着データが
どれだけ来るか」と「監査で何を証明する必要があるか」なのに、全軸均等の
表がそれを埋没させる。

### このskill適用時の出力

判断ゲート: フル適用（保存形式の選択。データが蓄積した後の変更は
実質不可逆）

**選択肢**
- A. SCD Type 2（有効期間つき差分履歴）
  — 勝つ条件: 変更頻度が低く「いつ何が変わったか」を問うクエリが主で、
  ストレージを差分最小で保ちたい場合
- B. デイリースナップショット（全量を日次で保存）
  — 勝つ条件: 「その日の時点で何が見えていたか」の再現が要件で、
  遅着・遡及訂正が日常的にある場合
- C. 併用（スナップショットを正とし、SCD2をその上のビュー/派生で提供）
  — 勝つ条件: Bの要件がありつつ、利用者がSCD2形式のクエリに慣れている場合

決定軸: 遡及訂正・遅着データの頻度 — SCD2は「変更イベントが正しく
観測できる」前提の構造であり、後から過去が書き換わる環境では有効期間の
繕い直しが恒常運用になる。ストレージ・クエリ難度は現代のDWHでは
決定的でない（差なし扱い）。

**前提と未知**
- 【仮定】ソース側で過去日付の訂正が月数回以上発生する
- 【確認済】現代の列指向DWHではスナップショットの重複はよく圧縮され、
  ストレージ差は判断を左右する規模にならない
- 未知: 監査要件が「変更の追跡」か「時点の再現」か
  — 安く潰す方法: 直近の監査・調査依頼の実例を1件見る（1時間）

## 推奨
案: B（デイリースナップショット）。SCD2ビューが必要になった時点でCへ拡張
根拠: 決定軸である遡及訂正への耐性はBが構造的に勝つ。スナップショットは
「観測した事実」の記録であり訂正が来ても壊れないが、SCD2は解釈を保存
するため訂正のたびに解釈の修復が要る。BからCへは無損失で拡張できるが、
AからBへは失われた日次観測を復元できない——この非対称性が決め手
最有力の反対理由: 「スナップショットは冗長で美しくなく、変更点が直接
見えない」— 正当だが、それは派生ビューで後から提供できる。逆方向
（差分から全時点を復元）は訂正が絡むと成立しない
後戻り条件: 遡及訂正の実測頻度が四半期に1回未満で、かつテーブルの
行数×日数がDWHのコスト警告ラインを超えたら、Aを再検討する

## 例3: ゲート判定の実例（素通し側）

素通し・即決も観測可能な出力である。以下の粒度で1行出す。

- 依頼「JSONのパース、標準ライブラリでいい？」
  → `判断ゲート: 素通し（G1: 特殊要件がない限り標準ライブラリが
  事実上の標準。選択肢が実質1つ）` → 一行で答えて終了

- 依頼「この変数名、fetched_at と retrieved_at どっちがいい？」
  → `判断ゲート: 即決（G3: 可逆・影響局所）` →
  `即決: fetched_at（コードベース内の既存表記と一致）` → 終了

- 依頼「（設計合意済みの件で）じゃあこの方式で実装して」
  → `判断ゲート: G2（判断済み。実装フェーズへ）` → 蒸し返さない。
  実装依頼として spec-first の領分に引き継ぐ

- 依頼「テーブルのパーティションキー、日付でいいよね？」
  → 一見G3に見えるが `判断ゲート: フル適用（保存形式・クエリ性能に
  不可逆の影響。「いいよね？」はユーザーの傾きなので反論先出し規則も
  適用）` — 可逆に見える不可逆の典型例
