# 落とし穴カタログ

セッションで実際に踏んだ罠を1件ずつ追記して育てる（/retrospective-codify が使える場面ならそちら経由でここに落とす）。

形式: 状況 / 兆候 / やりがちな誤り / 正しい対処 / 記録日。

## エントリ

### 検証の後回し
- 状況: 複数ファイルの変更を一気に進めている
- 兆候: 「あとでまとめてテストしよう」と考え始める
- やりがちな誤り: 最後に検証してエラーが複数原因で絡まり、切り分けに時間を溶かす
- 正しい対処: チェックポイントごとに検証し、エラーは1変更分の範囲で切り分ける
- 記録日: 2026-07-09（初期シード）

### パターン一致による誤診
- 状況: 既知の障害と似たシグナルが出た
- 兆候: ログや症状が過去のケースと「似ている」ことだけを根拠に対処を始めようとしている
- やりがちな誤り: 別原因の症状に過去の対処（再起動・設定変更）を適用して状態を悪化させる
- 正しい対処: 対処の前に、その操作を支持する証拠を今回のケースで確認する
- 記録日: 2026-07-09（初期シード）

### 手組み Token のバイトオフセットとテキストの不整合
- 状況: 形態素解析ルールのテストで、実テキストとは別に手組みの Token 列(surface_form を連結してバイト位置を振る)を渡し、マッチ結果の byte_start/byte_end で実テキストをスライスして検証する
- 兆候: テキストにスペースなど token 列に含めていない文字があっても、日本語の全角文字境界がたまたま揃うとテストが panic せずに通ってしまう(スライス内容の正しさまでは assert していないため)
- やりがちな誤り: 「テストが green だから正しい」と判断する。実際は byte_start/byte_end がずれた位置を指しており、たまたま char boundary に乗っていただけ
- 正しい対処: 手組み Token を使うテストでは、渡す text は token の surface_form を連結した文字列と完全に一致させる(別に用意した「自然な」文とは分けない)。一致しない構成にしたいなら、スライス結果の中身も assert に含めて検証する
- 記録日: 2026-09-14
