# fable-protocol — 長期タスク実行の型

長時間タスクで崩れやすいのは実装力ではなく、着手前の仕様固定と進行状態の維持。この型はそこだけを強制する。手順は省略せず順に実行する。

検証の指示は意図的に置いていない。モデル側が既定で自己検証するため、明示的に指示すると過剰検証になる（Opus 5 移行ガイドの指摘。削除しても能力低下は生じない）。Phase 0 で完了条件を検証可能な形にしておけば足りる。

## Phase 0: 仕様の固定（着手前・必須）

1. ゴール・制約・完了条件を自分の言葉で書き出す。
2. 完了条件は検証可能な形にする（「テスト X が通る」「画面 Y で Z が表示される」）。曖昧な点があれば着手前に**1回だけまとめて**ユーザーに確認する。以後は蒸し返さない。

## Phase 1: 分解とチェックポイント設計

3. タスクを 3〜7 個のチェックポイントに分解する。各チェックポイントは「検証可能な状態」で区切る（ビルドが通る、テストが通る、画面が出る）。
4. 進行状態を記録する（TodoWrite。セッションをまたぎうる長さなら progress ファイルも）。チェックポイント完了ごとに更新する。

## Phase 2: 実行ループ

5. チェックポイント単位で実装し、完了ごとに進行状態を更新する。
6. サブエージェントには費用が乗る——コンテキストの再確立、再探索、報告の読み直し。自分で数回のツール呼び出しで終わる作業には使わない。検証や再確認のためにも使わない（検証は本体のループの中でやる）。使うのは、互いに独立していて規模のある調査や修正を並列化するときだけ。1体で足りるなら1体にする。
7. 想定外の事実が出たら進行を止め、Phase 0 の仕様と突き合わせる。仕様が変わるならユーザーに確認、変わらないなら記録して続行する。

## Phase 3: 完了処理

8. 完了条件の充足を、証拠（コマンド出力・テスト結果）と対応付けて報告する。証拠のない「完了」を主張しない。未検証のものは未検証と明示する。
9. 得られた知見（ハマった点・最終的に通ったアプローチ）をメモリに記録する。繰り返し価値のあるものは /retrospective-codify でルール化する。踏んだ罠は references/pitfalls.md に追記する。
