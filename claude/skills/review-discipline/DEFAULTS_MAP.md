# 対応表：どのOpus既定を、どのルールで打ち消したか（review-discipline）

**この表は2026-07-10の独立検証（tefudaで18実行・グラウンドトゥルース付き）で全面較正済み。**
検証前の版は8主張中無修正で支持できるものがゼロだった（素のOpus＋ユーザー文脈が著者の想定より
はるかに強い）。以下は較正後。効果が実証された行はD4のみ、D5は文脈依存で半分。残りは
「予防規律としては無害だが素のOpusの既定を打ち消してはいない」または「観測されず」。

| # | 既定挙動の主張 | 打ち消すルール | 検証後の判定と実態 |
|---|---|---|---|
| D1 | 絞り込み指示を検出閾値として実装し、見つけたバグを黙って捨てる | 絶対規則＋圧縮リスト | **観測されず**。withoutも低重大指摘を「参考/補足」として報告し、報告段で黙って捨てる事態は一度も起きなかった。絶対規則が守る場所に敵はいない。実際の再現率喪失は報告段でなく**発見段（差分外を読まない＝D5/ステップ1）**で起きる。圧縮リスト自体は報告の可読性装置として有用だが、素のOpusの既定を打ち消してはいない |
| D2 | 低確信指摘の自己検閲。疑い級の指摘自体が出力に存在しない | ステップ2: 確信度3値タグ | **過大→較正**。素のOpusも不確実な論点は出す（散文の「補足」に埋め、確認手段の併記はない）。差は「疑い級が存在しない」ことではなく、**タグと確認経路の構造がない**こと。改善は検出でなく形式 |
| D3 | 楽観的承認（LGTM単体・根拠なしOK） | ステップ4: 判定ブロック強制 | **観測されず（藁人形）**。withoutは根拠つき承認を返し、1行差分でも自発的にテスト実行した例あり。「LGTM単体」は観測ゼロ。判定ブロックは形式の一貫化として有用だが既定の矯正ではない |
| D4 | 承認射程の誇張（静的読解なのに全面OK口調） | ステップ4: `未確認:` 欄の省略禁止 | **部分的に実在＝このskill唯一の一貫した実質改善**。withoutは確認したことは書くが未確認の範囲を明示しない。未確認欄の強制で検証射程が正直に区切られる（with 7/7） |
| D5 | 差分ハンクだけのレビューで呼び出し元型欠陥を構造的に見逃す | ステップ1: 読解範囲の強制＋新設の既存実装探索 | **文脈依存で半分実在**。coreの共有関数を触る差分では素のOpusも既定で呼び出し元を読む（R-E: without 2/2完全検出）。読まないのは**一見自己完結した新規機能コード**のとき（R-A: without全滅）。ステップ1が効く場面はここに限定 |
| D6 | 懸念の疑問文化（「〜は大丈夫でしょうか」） | ステップ2: 「壊れ方:」欄の強制 | **旧語法は観測されず（現行Opusで絶滅）**。ただし現代形の類型「認識しておくと良い」「頭の片隅に」という**行動経路のない軟性注記**は実在し、壊れ方欄の強制はこれには有効。矯正対象の記述を現代形に更新済み |
| D7 | 網羅の演出（全軸に「問題なし」の埋め草） | ステップ2: 該当なし軸の無言通過 | **観測されず**。withoutはどの実行でも軸別埋め草を書かなかった。with側の予防規律としては無害だが、「素のOpusの既定」という主張の根拠はない |
| D8 | typo差分の儀式化／1行差分の無確認スタンプ | ステップ0: R1/R2ゲート | **前半のみ機能**。ゲートは9/9正しく発火し儀式化を防いだ（with側の価値）。後半「素のOpusが無確認スタンプする」は**藁人形**——withoutも1行差分を2/2でテスト実行つきに精査した |

## 検証メモ

- empirical検証時の判定変数として頑健なのは:
  (1) **差分外読解の有無と読解先の正しさ**（呼び出し元・既存実装を実際に読んだか）。これが本skillで再現率に効く唯一の経路。※旧版は「絞り込み指示下で既知バグが出力に残るか＝再現率の直接測定」を(1)に置いていたが、2026-07-10検証で**前提不成立**と判明した——素のOpusの再現率喪失は報告段の抑制ではなく発見段の読解範囲で起きるため、この変数はD1+D2でなく実質D5を測る。再検証で再びD1の証拠に使わないこと、
  (2) `## 判定` `未確認:` `読んだ範囲:` `閾値未満（圧縮）:` の各行の存在（形式規律の測定。ここは確実に差が出る）、
  (3) 正確性系指摘における「壊れ方:」欄の充足率、
  (4) 指摘ゼロシナリオで `確認したこと:` に仮説→棄却が2件以上並ぶか。
  注意: 形式マーカーの文字列マッチ（(2)〜(4)）だけならwithは全勝に見える。検出力を測るにはグラウンドトゥルース付きの実在コードで欠陥表と突合しないと「形式は変わるが検出は変わらない」が見えない。
- 既存3枚との直交性: spec-first=着手前の仕様化、design-decision=選択の判断、operating-discipline=実行中の運転、本skill=他者の変更の検査。design-decisionと本skillはどちらも「ヘッジ禁止・根拠の強制」を含むが、あちらは自分の推奨へのコミット、こちらは他者のコードへの判定であり、成果物の書式（推奨ブロック vs 判定ブロック）も排他。
- 意図的に入れなかったもの: 指摘件数の下限ノルマ（「最低N件指摘せよ」）。再現率対策として一見直接的だが、モデルは件数ノルマを与えると水増しで応える（網羅の演出D7と同じ経路）。「捨てるな・タグを付けて全部出せ」という経路の統制のほうが、量のノルマより頑健に効く。
