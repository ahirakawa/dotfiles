# 対応表：どのOpus既定を、どのルールで打ち消したか

| # | Opusの既定挙動（打ち消す対象） | 打ち消すルール | 観測可能な挙動差 |
|---|---|---|---|
| D1 | **無判定の着手**。読み取り調査は行うが、「着手してよいか（曖昧さは残っていないか）」の判定を出力しないまま変更に入る | 絶対規則：変更ツール初回呼び出し前のゲート判定行の強制出力 | skill適用＝最初の**変更ツール呼び出し**より前に`ゲート:`行が出る（読み取り調査の先行は許容）。素のOpusとの差は判定の有無ではなく、判定が出力物になること |
| D2 | **事後の仮定申告**。解釈を隠しはしないが、実装が終わってから散文で自己申告する（外れた仮定はその時点で手戻り） | ステップ1（曖昧点リストの強制出力）＋ステップ3の出所タグ【明記/確定/推測】 | 仮定が**実装前に**タグ付き構造で出る。素のOpusは実装後に散文で申告するため、差は有無ではなくタイミングと形式 |
| D3 | **質問回避**。「聞きすぎるな」方向の調整が、聞くべき1〜2問すら省かせる | ステップ3：「外れたら作る物が変わる推測」に限定して最大4問。承認前の変更ツール呼び出し禁止 | 質問数が0→1〜4に変わる一方、些末な確認は増えない（限定条件が上限も下限も規定） |
| D4 | **親切心の追加実装**（gold-plating）。無依頼のエラー処理拡充・ついでのリファクタ | 非目標最低2件（「ついで」の先回り封じ）＋完了監査の「仕様外の追加リスト」 | 仕様外追加が「なし」または明示リストとして毎回出力される |
| D5 | **長期実装での合意の風化**。文脈圧縮と局所最適化で初期決定からドリフト | ステップ4：仕様のファイル永続化＋記憶でなくファイル再読での照合 | 複数ターン案件で`spec-<slug>.md`が生成され、監査時にReadが走る |
| D6 | **非監査型の完了報告**。検証自体は行うが、どの基準をどう確認したかの対応が追えない散文で報告する | 完了監査表（基準/検証方法/結果、未検証は未検証と明記） | 完了報告の直前に**基準単位で監査可能な表**が出る。素のOpusも検証はするが、基準との対応と未検証項目の明示が残らない |
| D7 | **実装中の無言の穴埋め**。途中で見つけた未定義点を現場判断で静かに処理 | `SPEC AMENDMENT:`ブロックの強制（軽微=報告して続行/重大=停止） | 仕様変更がgrep可能なマーカー付きでログに残る |
| D8 | **指示追従の過剰**。プロセスを与えると全案件に儀式として適用 | ステップ0のゲート（G1〜G4の素通し条件）＋ミニ仕様パス | typo修正が仕様書なしで即完了する。skillの「勝ち」は仕様を書くことではなく判定行を出すこと |
| D9 | **飾りの不変条件**。列挙はするが実装判断・テストに接続しない | 「破ると→」の強制併記＋帰結が書けない不変条件の削除ルール | 不変条件が必ず帰結文を伴い、受け入れ基準にその検証（例：POST非リトライのモック検証）が対応して現れる |

## 検証メモ

- empirical検証時の判定変数は「最初のファイル変更ツール呼び出しより前に `ゲート:` 行が存在するか」「仕様パス案件で完了監査表が存在するか」の2つが最も頑健。文字列マッチで判定でき、主観評価が不要。
- 意図的に入れなかったもの: 仕様のバージョニング・変更履歴管理。D5対策としては一見有効だが、個人利用ではD8（儀式化→無効化）誘発リスクが便益を上回る。`SPEC AMENDMENT:` ブロックがログ上の履歴として代替する。
