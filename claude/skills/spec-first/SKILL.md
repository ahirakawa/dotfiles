# spec-first: 着手前仕様化の強制手順

## 絶対規則

ファイルを変更する最初のツール呼び出し（Edit / Write / 変更を伴うBash）
より前に、必ずステップ0のゲート判定を行うこと。判定が素通しなら
そのまま着手し、ミニ仕様かフル仕様なら「仕様を先に書きます。」の1文を
出してから仕様に入る。判定を行わずに変更を開始してはならない。

## ステップ0: ゲート判定（過剰プロセス防止）

以下のいずれかに該当すれば仕様化を省略し、直ちに着手してよい。
判定は必ず行うが、「ゲート: 素通し（G2）」のような判定行は出力しない。
読み手にとっては手順のラベルであり、意味を持たないからである。

- **G1**: 変更が局所的（目安: 1ファイル・20行以内）で、依頼文と既存コード
  だけで完成形が一意に決まる。typo修正、ログ文言、定数変更、明白な単純バグ。
- **G2**: 再現手順と期待挙動の両方が依頼文に含まれるバグ修正。
- **G3**: ユーザーが「そのままやって」「仕様はいらない」等、プロセス省略を
  明示した。
- **G4**: ファイル変更を伴わない質問・調査・レビュー。

判定基準はこの一問: **「有能なエンジニアが2人いたら、この依頼から別の物を
作り得るか？」** 作り得るなら曖昧であり、仕様パスへ進む。迷ったら仕様パス。

### 軽量パス（ミニ仕様）

仕様パスのうち、変更が単一モジュールに閉じ、失敗しても revert 一発で
戻せる場合は「ミニ仕様」でよい: **目的・受け入れ基準・仮定** の3点のみ、
合計10行以内。ステップ1の列挙とステップ3の確認は行うが、ステップ2の
フルセクションは起こさない。

## ステップ1: 曖昧点の列挙

依頼文を以下の軸でスキャンし、**未定義点を箇条書きで列挙して出力する**。
列挙は内心で済ませてはならない。出力物である。

- 入力の範囲: 空・巨大・不正・重複・エンコーディング・想定外の型
- 失敗時の挙動: 途中失敗、部分成功、リトライ、再実行時の安全性（冪等性）
- 境界: 既存機能との共存、他の呼び出し元・依存先への影響
- 状態: 並行実行、実行順序、中断からの再開
- 完了の定義: 何ができたら終わりか、性能・規模の要件
- 運用: 誰がいつどう実行するか、失敗に気づく手段、戻し方

拾うべき最低ラインは「そこの決め方次第で作る物が分かれる分岐点」の全件。
スキャンして未定義点がゼロなら、その根拠を1行書いてステップ0のゲートに
戻り、素通しに切り替えてよい。

## ステップ2: 仕様を起こす（フル仕様のみ）

以下の固定セクションで仕様ドラフトを出力する。**セクションの省略は禁止**。
該当しない場合は「該当なし: <理由>」と明示する。

```
## 仕様ドラフト（合意待ち）
### 目的
### 非目標
### 入出力契約
### 不変条件
### 状態遷移
### 失敗モードと対処
### 受け入れ基準
```

セクション別の強制ルール:

- **不変条件**: 各項目に「**破ると→ <何が起きるか>**」を必ず併記する。
  帰結が書けない不変条件は不変条件ではないので削除する。

- **状態遷移**: ステートレスなら「該当なし: <理由>」と宣言する。無言の
  省略は禁止。

- **受け入れ基準**: 各項目に実行可能な検証方法（コマンド、具体的な入力と
  期待出力）を併記する。「正しく動くこと」「適切に処理されること」は禁止語。

- **非目標**: 今回やらないことを最低2つ書く。実装中に「ついで」で
  やりたくなりそうな拡張を先回りで封じる項目を優先する。
  非目標に書いた物は、実装中に追加してはならない。

## ステップ3: 仮定の明示と確認

仕様中の判断すべてに出所タグを付ける:

- **【明記】** 依頼文に書いてある
- **【確定】** コード・環境・過去の合意から一意に確定する
- **【推測】** あなたが埋めた

そのうえで:

1. **【推測】のうち「外れたら作る物が変わるもの」だけ**を質問にする。
   最大4問。AskUserQuestion が使えるなら使い、なければ番号付きで問う。
2. 残りの【推測】は「確認不要と判断した仮定」として仕様に残す。承認と
   同時にこれらも確定する。
3. 仕様全体を提示し、**ユーザーの明示的な承認を得るまで変更ツールを
   呼ばない**。
4. **非対話文脈の規定**: ユーザーが即応できない文脈（非対話実行・
   バックグラウンド・バッチ）では、**フル仕様**は実装せず、仕様と質問を
   提示して停止する。**ミニ仕様**は安全側（後方互換側）のデフォルトで
   実装まで進んでよいが、完了報告の直後に「確認していない前提」として
   採用した【推測】を再掲する。どちらを選んだかを仕様の冒頭に1文で書く。

## ステップ4: 実装とドリフト監査

- **仕様の永続化**: 実装が複数ターンに渡りそうなら、合意した仕様を
  scratchpad（またはユーザー指定の場所）に `spec-<slug>.md` として保存し、
  監査時は記憶ではなくこのファイルを再読して照合する。

- **仕様修正プロトコル**: 実装中に仕様の穴・矛盾を発見したら、現場判断で
  黙って埋めずに `SPEC AMENDMENT:` で始まるブロックを出力する。
  作る物が変わる修正なら停止してユーザーに確認、変わらない軽微な補完なら
  報告したうえで続行してよい。

- **完了時の確認**: 完了報告の直前に、以下を必ず出力する。「完了監査」
  という見出しは付けず、「確かめたことは次のとおりです。」の1文から
  始める。
  1. 受け入れ基準の表: `基準 / 検証方法 / 結果`。実行していない検証は
     「未検証」と書く。「満たしているはず」は結果ではない。
  2. 頼まれていないが足したもののリスト（なければ「なし」と明記）。挙げた
     物は revert するか、残す理由を添えてユーザー判断に回す。
  3. 「やらないと決めたことには触れていません。」の1文。触れた場合だけ、
     何に触れたかを書く。

## 出力言語

ゲート判定・曖昧点リスト・仕様・質問・監査は、すべてユーザーが使用して
いる言語で書く。

## このskillの成果物一覧（省略不可）

- ゲート判定（全依頼で必須。ただし判定行は出力しない）
- 曖昧点リスト（仕様パスで必須）
- 仕様ドラフト（フル仕様パスで必須。固定セクション）
- 仮定の出所タグと確認質問（仕様パスで必須）
- SPEC AMENDMENT ブロック（実装中に穴を見つけた場合）
- 完了時の確認の表（仕様パスの完了時に必須。「完了監査」の見出しは付けない）
