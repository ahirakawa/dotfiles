# worked examples: 曖昧な一言依頼 → 起こした仕様

抽象論ではなく、実際の依頼文と実際の出力の対でこのskillの挙動を定義する。
迷ったらこのファイルの粒度に合わせる。

---

## 例1: 「CSVをDBに取り込むスクリプト書いて」

### 規律なしの既定挙動（こうなってはいけない）

pandas で read_csv → to_sql する20行のスクリプトを即座に書く。
エンコーディングはUTF-8、重複は無視、失敗したら例外で全停止、再実行したら
二重投入——これらすべてを無言で決めており、どれも出力に現れない。
ユーザーが二重投入に気づくのは本番データが壊れた後である。

### このskill適用時の出力

ゲート: フル仕様（取り込み先・失敗時挙動・再実行の扱いが未定義。
エンジニア2人なら別物を作る）

**曖昧点リスト**
- 取り込み先のテーブルは既存か新規か。既存ならスキーマ不一致時の挙動は
- 同じCSVを2回流したらどうなるべきか（追記/置換/スキップ/エラー）
- 不正行（列数不足・型不正）の扱い: 全停止か、スキップして最後に報告か
- CSVの規模感（数千行かGB級か。ロード方式が変わる）
- 文字コードとヘッダ行の有無
- 誰がいつ実行するか（手動一回きり / 定期実行）

**仕様ドラフト（合意待ち）**

### 目的
指定ディレクトリのCSVを既存テーブルに取り込み、再実行しても安全な
一回きりの手動スクリプトを提供する。

### 非目標
- 定期実行のスケジューリング（今回は手動実行のみ）
- スキーマの自動進化（列が増えたCSVはエラーにする）

### 入出力契約
- 入力: パス引数1つ。UTF-8、ヘッダ行あり【推測】
- 出力: 取込件数・スキップ件数・不正行の行番号を標準出力に報告
- 終了コード: 全件成功=0 / 一部不正行スキップ=0（報告あり）/ 接続失敗等=1

### 不変条件
- 同一CSVの再実行で行が増えない（キー列で冪等化）。
  破ると→ 失敗時の「とりあえずもう一回」で二重集計になり、下流の数値が壊れる
- 不正行があっても正常行の取り込みは完遂する。
  破ると→ 100万行中1行の型不正で全体が失敗し、手作業の切り分けが発生する

### 状態遷移
該当なし: 一回きりのバッチであり中断再開は再実行で代替する（冪等なので安全）

### 失敗モードと対処
- DB接続失敗 → 即時終了コード1、何も書き込まない
- 型不正行 → スキップして行番号を収集、最後にまとめて報告
- キー列がnull → 不正行として同上

### 受け入れ基準
- 正常CSV 3行 → `SELECT count(*)` が +3
- 同じCSVをもう一度実行 → count が変わらず、スキップ3件と報告される
- 1行だけ型不正のCSV → 正常行は入り、終了コード0、不正行番号が出力される

**仮定と確認**（【推測】のうち作る物が変わる2点のみ質問）
1. 再実行時は「同一キーはスキップ」でよいか、それとも「置換（upsert）」か
2. 不正行は「スキップして続行」でよいか、それとも「1行でもあれば全停止」か

確認不要と判断した仮定: UTF-8・ヘッダあり（外れても修正が1行で済む）

## 例2: 「このAPIクライアントにリトライ入れて」

### 規律なしの既定挙動（こうなってはいけない）

全メソッドに一律で指数バックオフ3回を巻く。POSTも区別なくリトライする。
タイムアウトで「失敗」と判定された注文作成が実はサーバ側で成功しており、
リトライで二重注文になる。リトライは「入れるだけなら簡単、安全に入れるのが
仕様問題」の典型であり、まさにこのskillが存在する理由の案件である。

### このskill適用時の出力

ゲート: フル仕様（何をリトライ対象とするかで安全性が根本から変わる）

**曖昧点リスト**
- リトライ対象: 全メソッドか、冪等なもの（GET/PUT/DELETE）だけか
- 非冪等リクエスト（POST）のタイムアウトをどう扱うか
- リトライ判定: ステータスコード（429/503）か、接続エラーも含むか
- 回数と待ち: 何回まで、バックオフとジッタの有無
- Retry-After ヘッダを尊重するか
- 呼び出し元への見え方: リトライは透過か、最終失敗時に試行回数を伝えるか

**仕様ドラフト（合意待ち）**

### 目的
一時的な障害（429/503/接続断）で呼び出し元が失敗しないよう、安全な
リクエストのみ自動リトライする。

### 非目標
- サーキットブレーカー（今回は単純リトライのみ）
- 呼び出し元コードのシグネチャ変更（既存呼び出しは無修正で動く）

### 入出力契約
- 既存メソッドのシグネチャ・戻り値は不変
- 最終失敗時の例外に試行回数と最後のステータスを含める

### 不変条件
- 非冪等リクエスト（POST等）は自動リトライしない。
  破ると→ タイムアウト後にサーバ側で成功していた場合、二重作成・二重課金
  が起きる。これはバグ報告ではなくインシデント報告になる
- リトライ待ち時間にはジッタを入れる。
  破ると→ 障害復旧の瞬間に全クライアントが同期して再送し、リトライストーム
  で相手を再度倒す
- 総リトライ時間に上限を設ける。
  破ると→ 呼び出し元のタイムアウト設計が無意味になり、障害時に処理が
  無期限に滞留する

### 状態遷移
該当なし: リトライ状態はリクエスト単位でローカルに閉じ、インスタンスに
状態を持たない（持つならサーキットブレーカーであり非目標）

### 失敗モードと対処
- 429 → Retry-After があれば従い、なければ指数バックオフ
- 503 / 接続断 → 冪等メソッドのみ指数バックオフ（上限3回、ジッタあり）
- 4xx（429以外）→ リトライしない（再送しても結果は同じ）

### 受け入れ基準
- モックが 503, 503, 200 を返すとき GET が成功し、試行3回が記録される
- 同条件で POST は1回で失敗し、リトライされない（モックの呼び出し回数=1）
- 全滅時の例外メッセージに試行回数が含まれる

**仮定と確認**
1. POSTのリトライ除外でよいか。もし業務上POSTにも冪等キー等の仕組みが
   あるなら設計が変わるため、これだけは着手前に確認したい

## 例3: ゲート判定の実例（過剰プロセス防止側）

素通しの判定も観測可能な出力である。以下の粒度で1行出す。

- 依頼「READMEのtypo直して」
  → `ゲート: 素通し（G1: 1ファイル局所変更、完成形一意）` → 即実装

- 依頼「f(None)で落ちる。空リストを返すのが期待」
  → `ゲート: 素通し（G2: 再現と期待挙動あり）` → 即実装

- 依頼「日付パース処理をutilに切り出して」
  → `ゲート: ミニ仕様（単一モジュール、revert一発）`
  ```
  目的: 3箇所に重複する日付パースを util に集約。挙動変更なし
  受け入れ基準: 既存テスト全通過 / 3箇所の呼び出しが新utilを参照 /
                重複実装が削除されている
  仮定:【推測】タイムゾーン処理も現状のまま移す（統一はしない）
  ```
  → 仮定に異論なければ着手、の一言を添えて短く確認

- 依頼「ログをいい感じに整理して」
  → `ゲート: フル仕様（「いい感じ」はエンジニア2人が別物を作る典型。
     レベル方針・出力先・既存ログの互換・構造化の有無がすべて未定義）`
